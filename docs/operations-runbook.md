This runbook describes the release path implemented in `platform/`; website deployment is live, while package publication is not. The intended public domain is `getpatched.dev`, with `repo.getpatched.dev` and `early.getpatched.dev` for package channels. The canonical Worker origin was added in PR [#65](https://github.com/getpatched/platform/pull/65) and deployed successfully from `main` commit `31cb311fc1cf06c27304423ee517408ca0d6f0aa` in [run 40798711459](https://github.com/getpatched/platform/actions/runs/40798711459). Deployment output confirmed the `getpatched-release-staging` R2 binding and all three custom domains, and public smoke checks passed for `/` and `/account`. The later documentation-only merge PR [#66](https://github.com/getpatched/platform/pull/66) also passed the main-merge deployment in [run 40799426159](https://github.com/getpatched/platform/actions/runs/40799426159). Post-deployment probes returned HTTP 503 for OAuth `/auth/github` and public Focal `InRelease`; the anonymous early `InRelease` route returns HTTP 401. These responses mean OAuth remains unconfigured and no signed public index is active. The bucket has no published package objects. GitHub Sponsors enrollment and package-release configuration remain incomplete. Deployment evidence and live repository endpoint responses are recorded in the [GetPatched domain plan](getpatched-dns-cutover-plan.md).

## Local verification

On macOS, temporary-key tests can fail when GPG-agent IPC does not start, even with a short temporary path. The most recent local run with `TMPDIR=/tmp python3 -B -m unittest discover -s verification -p 'test_*.py' -v` ran 85 tests: 83 passed and two signature-generation tests errored because `gpg-agent` could not be reached (`IPC connect call failed; No agent running`). Do not count these as passing local signature checks. The GitHub-hosted Linux verification suite passed in [run 40793133586](https://github.com/getpatched/platform/actions/runs/40793133586). Use a functioning GPG-agent environment for local signing verification; do not weaken or skip the signature tests to hide this host limitation.

## Deployment gates

The public website deployment is active. The deployment workflow verifies the domain through live smoke checks and uses the protected `getpatched-worker-deploy` environment. Package publication has additional gates and must stay disabled until those checks pass:

1. The active `getpatched.dev` zone and nameserver delegation are verified, and Wrangler has provisioned the Worker custom domains; no additional nameserver change is needed. This is a new registration with no pre-registration zone export to restore. Do not copy records from the former `apt.to` domain or add guessed records manually.
2. The website and sponsor portal belong on `getpatched.dev`; the public and early archives belong on `repo.getpatched.dev` and `early.getpatched.dev`. `worker/wrangler.jsonc` declares all three as Worker custom domains so one Worker can serve the site assets and two archive channels. The apex and `/account` routes passed smoke checks. Live checks also confirmed the public Focal `InRelease` route returns HTTP 503 because no signed metadata is published and the unauthenticated early route returns HTTP 401. These confirm route behavior, not a live package archive or sponsor access. Cloudflare requires an active zone before creating Worker custom domains ([Custom Domains documentation](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)); declarations alone do not prove routing, which is why the live checks above are recorded.
3. The `getpatched-release-staging` R2 bucket exists in the verified Cloudflare account with Standard storage in EEUR, currently contains 0 B, and is attached to the deployed Worker. Keep the bucket private; `r2.dev` is disabled and must stay disabled.
   To exercise the deployed binding without enabling release publication, dispatch **Verify deployed R2 binding** from `main`. The OIDC-protected `getpatched-index-build` job calls the Worker self-test route; it writes one uniquely named object under `diagnostics/r2-self-test/`, verifies metadata, SHA-256 and bytes on readback, deletes the object, and confirms it is absent. It does not set `GETPATCHED_REPOSITORY_ENABLED`, access package objects, publish releases or modify repository indexes. A successful run is the required proof that the production R2 binding supports real write/read/delete operations. If cleanup fails, the workflow reports the exact diagnostic key so it can be removed before retrying.
4. The organization rename is complete, and GitHub currently lists `getpatched/platform`, `getpatched/packaging-libxml2`, and `getpatched/packaging-libarchive`. The `getpatched-signing` environment has no required human reviewer under the maintainer's single-operator policy; signed-tag identity verification and all package verification gates still apply. Keep `GETPATCHED_REPOSITORY_ENABLED` unset until repository publication gates (including the private R2 binding, host routing, signing key, and protections) are verified. Website deployment is independent of package signing and publication.
5. Configure the required Worker secrets and vars only in the verified Cloudflare account: `GITHUB_TOKEN`, `GETPATCHED_RELEASE_TAG_SIGNER`, `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`, `SPONSOR_GRAPHQL_TOKEN`, and `SPONSOR_WEBHOOK_SECRET`. There is no tier allowlist: every active individual GitHub Sponsors tier qualifies. Organization sponsorships remain closed until securely mapped to one explicitly authorized GitHub user. Scope `GITHUB_TOKEN` to Contents read/write on only `getpatched/packaging-libxml2` and `getpatched/packaging-libarchive`; the Worker uses it for signed-tag verification and GitHub Release assets. The non-secret canonical `PUBLIC_ORIGIN` is pinned to `https://getpatched.dev` in `worker/wrangler.jsonc` and deploys with the Worker. Set `GETPATCHED_RELEASE_TAG_SIGNER` to the exact GitHub login allowed to sign package release tags. The Worker requires GitHub's cryptographic verification result and resolves the signed tagger email to that account through GraphQL; GitHub documents this email-to-user association as nullable, so the signing email must be associated with the configured GitHub account or release verification fails closed. Hosted staging and snapshot workflows authenticate with tightly constrained GitHub OIDC claims. Do not configure `RELEASE_ADMIN_TOKEN` for routine operation: it is an optional static bearer credential that bypasses OIDC workflow identity checks and grants release-admin access. Leave it unset unless a separate, concrete emergency-operation need justifies that bypass. Do not put secret values in Git, Actions artifacts, public workflow logs, or command output.
6. Enroll `getpatched` in GitHub Sponsors from the organization-owner account. GitHub's current [organization setup guide](https://docs.github.com/en/sponsors/receiving-sponsorships-through-github-sponsors/setting-up-github-sponsors-for-your-organization) requires a supported legal operating region, contact details, choosing bank or fiscal-host payouts during sign-up, tax information, 2FA on the owner's GitHub account, and GitHub approval. Complete those identity, payout, and tax steps in GitHub; do not put that information in this repository. After approval, verify the live organization listing, receiving eligibility, webhook configuration, and API permissions. Choose and record the intended monthly tier price before publishing: GitHub does not let maintainers edit a published tier's price; changing it requires retiring that tier and creating another. GitHub supports up to 10 monthly and 10 one-time tiers. The Worker fails closed when sponsor data is missing or stale. Do not start the seven-day clock or claim sponsor access works until these live checks pass.

## Worker deployment workflow

`.github/workflows/worker-deploy.yml` automatically verifies and deploys the Worker and static site on pushes to `main` (including merges), then checks `https://getpatched.dev/` and `/account`. A manual dispatch remains available from `main` and requires `confirm_production: true`. The `getpatched-worker-deploy` environment contains the Cloudflare account ID and ongoing deployment token; restrict its deployment branches to `main`. Under the maintainer's single-operator policy, neither website deployment nor package signing waits for a human reviewer. Signed-tag identity checks and the full package verification and publication gates remain in force.

The Worker was created in the initial deployment. That bootstrap used a dedicated temporary token with Workers `Admin` at the product scope and `Workers Routes Write` limited to the `getpatched.dev` zone; it was revoked and its GitHub environment secret removed after deployment. Routine automatic deployments use the existing `CLOUDFLARE_API_TOKEN`, with Workers `Editor` plus zone-scoped `Workers Routes Write`; do not retain product-level `Admin` in CI. Cloudflare's CI guide requires a token and account ID in CI secrets ([GitHub Actions documentation](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)).

The public catalogue and `/account` status page are deployed before sponsorship enrollment and OAuth are complete; the account page reports unavailable sign-in accurately. Missing sponsor and release credentials must fail closed and must not publish packages. Do not enable package signing/publication as part of website deployment. Verify the private R2 binding before staging any packages.

GitHub's `sponsorshipsAsMaintainer(activeOnly: true)` result is the entitlement authority: it includes every individual sponsorship still active now, at every tier. A recurring sponsor whose cancellation is pending remains active until the paid period ends; a one-time sponsorship is eligible only while GitHub reports it active. Organization sponsorships are not mapped to a GitHub user and do not grant account access. Webhook deliveries for creation, tier changes, pending cancellation, and cancellation trigger reconciliation, but the authoritative active-only snapshot controls access. The Worker also refreshes every 15 minutes. A successful refresh removes access when GitHub no longer reports the sponsorship active; failed refreshes fail closed when the snapshot reaches its 30-minute freshness limit. That is a bounded reconciliation delay, not a locally inferred expiry timestamp. See [GitHub's Sponsors GraphQL reference](https://docs.github.com/en/graphql/reference/sponsors#sponsorship), [sponsorship webhook payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#sponsorship), [Sponsors billing](https://docs.github.com/en/billing/concepts/third-party-payments/github-sponsors), and [organization tier setup](https://docs.github.com/en/sponsors/receiving-sponsorships-through-github-sponsors/setting-up-github-sponsors-for-your-organization).

The `getpatched.dev` Worker is connected and the apex and `/account` routes pass live smoke checks. The ongoing deployment credential was verified by a follow-up deployment after the temporary bootstrap credential was revoked. For future changes, confirm the protected deployment environment still has the ongoing token before merging a change that triggers deployment. Do not expose credential values or account-specific credential metadata in Git, logs, artifacts, screenshots, or chat.

Keep Cloudflare credentials separated by operation. Cloudflare's current [Workers roles and permissions](https://developers.cloudflare.com/workers/authorization/workers/) documentation says creating a new Worker requires the `Admin` role at the Workers product scope. The initial deployment used a dedicated seven-day token with product-level `Admin` and Zone > Workers Routes > Write limited to `getpatched.dev`; the token was revoked after Worker creation and `CLOUDFLARE_BOOTSTRAP_TOKEN` was removed from GitHub. Never leave product-level `Admin` in routine CI. This is completed deployment history; do not create another bootstrap token for routine releases.

The current `wrangler.jsonc` declares three Custom Domains. Cloudflare says Custom Domains do not support per-Worker roles, so the documented ongoing scope is Workers `Editor` at the product scope plus Zone > Workers Routes > Write limited to `getpatched.dev`. The existing `CLOUDFLARE_API_TOKEN` successfully deployed the Worker after the bootstrap credential was revoked. Protect it in the `getpatched-worker-deploy` environment and do not describe it as per-Worker scoped. The Worker binding does not require separate R2 or KV permissions to deploy. Do not accept the broad **Edit Cloudflare Workers** template defaults unchanged; omit DNS, R2, KV, tail, user, and unrelated write access.

Store the deployment token and required account identifier only as `getpatched-worker-deploy` environment secrets. If the token UI or pinned `wrangler deploy` requires broader access than these documented roles, stop and verify the exact operation before widening scope. See Cloudflare's [token creation guide](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/), [permission reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/), and [Workers GitHub Actions guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/). Do not reuse this token for registrar or DNS changes. A DNS operator credential, if API-based DNS changes are chosen, should have only Zone DNS Read/Edit access to the verified `getpatched.dev` zone and should not be stored in GitHub. Nameserver delegation itself is a separate registrar operation. If a separate CI utility must call the R2 S3 API, create a distinct R2 Object Read & Write token scoped only to `getpatched-release-staging`; do not grant account-wide R2 Admin access. Cloudflare documents [R2 token permissions](https://developers.cloudflare.com/r2/api/s3/tokens/). The package signing environment's independent review requirement remains separate from this website deployment environment.

## Candidate build and release

1. Review the package source, patches, candidate evidence, and `packages.json` policy. Keep libxml2 on the seven-day policy and libarchive on immediate-public policy; verify current base versions and checksums before each new release.
   **Support boundary:** these builds use the latest publicly available Focal sources. Ubuntu Pro/ESM installations and upgrades are outside pilot support and are not release gates. The `+getpatched1` version may sort above later Canonical `+esm` revisions; users relying on ESM must not assume automatic upgrades while using these packages. No Ubuntu Pro token or synthetic ESM upgrade fixture is required for release eligibility. The OSV vendor comparison uses the public `Ubuntu:20.04:LTS` ecosystem; its baseline response is supporting evidence, while the installed regressions and GetPatched package-aware scan are the release gates.
2. From the GitHub Actions UI, dispatch **Package build and installed regressions** with the selected package and its full commit SHA from `getpatched/focal`. Require the complete build, vulnerability comparison, installed regression, consumer checks, and signed local focal-client smoke tests to pass. Preserve the run URL and artifacts in `EVIDENCE.md`.
3. With `GETPATCHED_REPOSITORY_ENABLED=true`, a successful manual package run triggers **Private binary staging**. That workflow checks out trusted platform tooling, rebuilds the pinned package, compares exact binary/source hashes, stages gated binaries privately, and publishes complete corresponding source assets publicly. It must target `https://repo.getpatched.dev` and use the `getpatched-signing` environment. Confirm the final state and hashes before treating the release as staged.
4. **Publish signed APT repository snapshots** builds public and early indexes in `getpatched-index-build`, passes the registered snapshot IDs to `getpatched-signing`, verifies index hashes, signs with the configured fingerprint, uploads immutable snapshots, and switches each channel pointer after R2 readback succeeds. The workflow also runs every 15 minutes to detect newly eligible releases and promote releases whose 168-hour deadline has passed; if the release IDs match a healthy active snapshot, it skips package downloads, index generation, signing and publication. The Worker verifies active snapshot eligibility and every stored index object's size, SHA-256 and identity metadata before reporting it as healthy. A manual dispatch may set `force_refresh` to rebuild unchanged metadata, such as when an operator needs to repair a damaged active snapshot. For recovery, dispatch this workflow from `main` with operation `rollback`, choose exactly one channel, and provide its full retained snapshot ID; the protected signing job revalidates the existing manifest, channel eligibility, and every R2 object hash before atomically restoring that channel pointer. No package bytes or GitHub Release assets are rebuilt or replaced.
5. **Prune repository storage** runs weekly at 03:25 UTC Sunday or by manually dispatching operation `prune`, under the protected `getpatched-signing` environment and the same workflow concurrency group as publication and rollback. Activation history tracks the six most recently activated snapshots per channel. Each run verifies the active manifest, eligibility and every active R2 object; rollback activation repeats those checks before switching pointers. From history, retention keeps only complete snapshots whose package releases remain eligible and removes older unreferenced objects. It processes at most 50 expired snapshots and 50 expired builds per channel per run, returning pending counts so a backlog can be cleared by later weekly runs or a manual prune. It keeps only the newest registered unsigned build during its first 24 hours, then removes it and older build staging. The release reconciler separately retains package and source R2 staging copies for 30 days after public publication; it deletes those copies only after auditing the immutable GitHub binary and source releases and their asset hashes. If a public audit fails, the R2 recovery copies remain and the reconciler retries later. A manual prune can run snapshot/build cleanup outside the weekly schedule.
6. Confirm the workflow run and Worker responses for both channels. The public index must exclude sponsor-period binaries; the early index and binary downloads must require valid sponsor credentials. Test invalid, expired, and anonymous credentials and verify that no redirect or cache path exposes a gated binary.
7. Install from a fresh focal amd64 client with the published keyring and scoped `Signed-By` configuration. Test anonymous libarchive installation and sponsor-authenticated libxml2 installation, `apt-get source`, package checksums, cross-host redirects, and post-promotion URLs. Record exact client output and workflow IDs.

## Recovery and key custody

- If package verification, private staging, signing, or snapshot activation fails, stop the release path and retain the previous active snapshot. Do not retry by changing bytes under an existing package version or snapshot ID.
- A rollback changes repository metadata only; it does not downgrade packages already installed by clients, and clients may retain signed metadata caches for up to five minutes. After activation, verify the channel's `InRelease` and run `apt-get update` on a clean client. The Worker rejects a snapshot whose releases are no longer eligible or whose stored bytes fail manifest readback. Snapshot/build retention and the 30-day public-release staging interval are implemented in source but remain inactive until the Worker, R2 binding and protected GitHub environments are deployed and verified. Do not claim production cleanup until the protected retention workflow and release reconciler have run successfully against the real bucket.
- Keep the two-year RSA-4096 metadata signing key only in the protected `getpatched-signing` environment. The public key and primary fingerprint are published at `/keys/getpatched-archive-key.asc` and `/keys/getpatched-archive-key-fingerprint.txt`; verify the fingerprint over an independent channel before trusting it and record the public-key checksum when preparing client installation instructions. No production snapshot has been signed or published, and no rotation drill has been completed. For rotation, prepare the replacement key and client trust transition, verify a signed test snapshot, then follow the separately reviewed rotation procedure.
- Package release tags are accepted only when GitHub verifies the annotated tag and its tagger resolves to `GETPATCHED_RELEASE_TAG_SIGNER`; GitHub may return no account association for an email, and in that case publication stops. Keep the maintainer's GitHub account limited to the specifically approved release-signing keys and ensure the tagger email is associated with that account. Rotate a package tag key by first registering and testing the replacement key on the approved account; changing the allowed GitHub account requires a separate review and configuration update. The allowlist is account-level, not a pinned GPG fingerprint; no production signer account or tag key is configured yet.
- On suspected key compromise, disable the signing environment and stop snapshot publication. Preserve evidence and the last known-good snapshot; do not publish an unreviewed replacement key or claim old package copies were revoked.
