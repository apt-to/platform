# AptTo operations runbook

This runbook describes the intended release path implemented in `platform/`. It is not evidence of a live deployment. As of 26 October 2026, read-only Cloudflare inventory confirms the correct account and zone, but no AptTo Worker, R2 bucket, or Pages project exists there; the zone is pending with no DNS records. Repository hostnames, GitHub signing environment, and Sponsors enrollment are not live.

## Deployment gates

Do not deploy until all of these checks are complete:

1. Use the existing Cloudflare account identified in the project setup as **Diderichsens**. The read-only API returned the display name **Diderichsen** for the credential's account; match the account and `apt.to` zone by their verified IDs before any mutation. The API found the full zone in `pending` status with zero records. Public DNS still resolves through Afternic nameservers to parked-domain addresses for the apex and repository subdomains. Preserve all existing records and services. Do not change nameservers or deploy custom domains until the active Cloudflare zone and a safe DNS path are verified; the current Afternic delegation is a deployment blocker.
2. The website and sponsor portal belong on `apt.to`; the public and early archives belong on `repo.apt.to` and `early.apt.to`. `worker/wrangler.jsonc` now declares all three as Worker custom domains so one Worker can serve the site assets and the two repository channels. Cloudflare requires an active zone before creating Worker custom domains ([Custom Domains documentation](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)); adding these declarations does not prove DNS, certificates, or routing are live.
3. In the verified Cloudflare account, create or confirm the R2 bucket named `aptto-release-staging`, then confirm the Worker binding in `worker/wrangler.jsonc` points to that bucket. Keep the bucket private; do not enable `r2.dev` or public bucket access.
4. GitHub Actions environments `aptto-index-build` and `aptto-signing` already exist in `apt-to/platform` and are limited to the main branch. The builder has no reviewer requirement and needs no secrets. The signing environment requires one reviewer and blocks self-review; the configured reviewer is currently the only organization member, so release approval is not possible until a second trusted reviewer is added. The signing environment currently has no secrets or variables. Once an eligible reviewer and signing key are configured, store `APTTO_SIGNING_KEY_ARMORED` as an environment secret and `APTTO_SIGNING_FINGERPRINT` as an environment variable. Keep repository variable `APTTO_REPOSITORY_ENABLED` unset until the Worker, private R2 binding, host routing, signing key, and environment protections have been verified. This keeps both private staging and repository snapshot publication dormant. Set it to `true` only after these deployment gates pass; this enables private staging after package verification, the scheduled promotion reconciler, and manual snapshot publication.
5. Configure Worker secrets and vars in the verified Cloudflare account: `GITHUB_TOKEN`, `APTTO_RELEASE_TAG_SIGNER`, `RELEASE_ADMIN_TOKEN`, `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`, `SPONSOR_GRAPHQL_TOKEN`, `SPONSOR_ALLOWED_TIER_IDS`, `SPONSOR_WEBHOOK_SECRET`, and `PUBLIC_ORIGIN`. Set `APTTO_RELEASE_TAG_SIGNER` to the exact GitHub login allowed to sign package release tags. The Worker requires GitHub's cryptographic verification result and resolves the signed tagger email to that account through GraphQL; GitHub documents this email-to-user association as nullable, so the signing email must be associated with the configured GitHub account or release verification fails closed. Set `PUBLIC_ORIGIN` to `https://apt.to` only after the portal's apex hosting and OAuth callback are deliberately configured. Do not put secret values in Git, Actions artifacts, public workflow logs, or command output.
6. Verify the `apt-to` GitHub Sponsors listing, receiving eligibility, tier IDs, webhook configuration, and API permissions. The Worker fails closed when sponsor data is missing or stale. Do not start the seven-day clock or claim sponsor access works until these live checks pass.

## Worker deployment workflow

`.github/workflows/worker-deploy.yml` is a manual production entry point. It runs only from `main`, requires the `confirm_production` input, and remains dormant unless repository variable `APTTO_WORKER_DEPLOY_ENABLED` is exactly `true`. Before enabling it, create the `aptto-worker-deploy` GitHub environment with an independent required reviewer and self-review prevention; add `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as environment secrets. Create a dedicated Cloudflare token using the **Edit Cloudflare Workers** permission template, scoped to the verified AptTo account and only the resources this Worker needs; never copy the existing account key into GitHub. Cloudflare's current CI guidance requires the API token and account ID in CI secrets ([GitHub Actions documentation](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)). The workflow runs the Worker and Python acceptance suites before deployment and checks `https://apt.to/` and `/account` afterward. Keep the enable variable unset until the zone is active, DNS migration is approved, the private R2 bucket and Worker runtime secrets are configured, and environment protection is verified.

GitHub's `sponsorshipsAsMaintainer(activeOnly: true)` result is the entitlement authority: `activeOnly` means sponsorships still active now, and GitHub's billing guidance says a recurring sponsorship's current paid period continues until its next renewal after cancellation. A one-time sponsorship may also be eligible while GitHub reports it active; GitHub documents that a one-time sponsorship period expires, so do not turn it into a permanent entitlement or invent a local expiry period. The `sponsorship` webhook's `cancelled` action is emitted only after the last billing cycle ends and is not sent for one-time sponsorships. Treat webhook deliveries as reconciliation markers, not as direct entitlement changes; the Worker refreshes the active sponsorship and approved tier snapshot every 15 minutes. A successful refresh removes access when GitHub no longer reports the sponsorship active; if refreshes fail, access fails closed when the snapshot reaches its 30-minute freshness limit. This is a bounded reconciliation delay, not an exact per-sponsor expiration timestamp: the selected GitHub query exposes current active status, and the Worker does not infer an expiry date. See [GitHub's Sponsors GraphQL reference](https://docs.github.com/en/graphql/reference/sponsors#sponsorship), [sponsorship webhook payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#sponsorship), [Sponsors billing](https://docs.github.com/en/billing/concepts/third-party-payments/github-sponsors), and [organization tier setup](https://docs.github.com/en/sponsors/receiving-sponsorships-through-github-sponsors/setting-up-github-sponsors-for-your-organization).

The existing Cloudflare credential was located locally and used only for read-only API checks against the account and `apt.to` zone by ID. The account display-name difference described above is unresolved at the label level; use IDs for any future account selection. Keep the existing credential local and never copy it into GitHub. Before CI or production deployment, determine its least-privilege scopes and use a dedicated scoped credential in the service's native secret store. Do not use Eupry-scoped Cloudflare credentials for AptTo.

## Candidate build and release

1. Review the package source, patches, candidate evidence, and `packages.json` policy. Keep libxml2 on the seven-day policy and libarchive on immediate-public policy; verify current base versions and checksums before each new release.
2. From the GitHub Actions UI, dispatch **Package build and installed regressions** with the selected package and its full commit SHA from `aptto/focal`. Require the complete build, vulnerability comparison, installed regression, consumer checks, and signed local focal-client smoke tests to pass. Preserve the run URL and artifacts in `EVIDENCE.md`.
3. With `APTTO_REPOSITORY_ENABLED=true`, a successful manual package run triggers **Private binary staging**. That workflow checks out trusted platform tooling, rebuilds the pinned package, compares exact binary/source hashes, stages gated binaries privately, and publishes complete corresponding source assets publicly. It must target `https://repo.apt.to` and use the `aptto-signing` environment. Confirm the final state and hashes before treating the release as staged.
4. **Publish signed APT repository snapshots** builds public and early indexes in `aptto-index-build`, passes the registered snapshot IDs to `aptto-signing`, verifies index hashes, signs with the configured fingerprint, uploads immutable snapshots, and switches each channel pointer after R2 readback succeeds. The workflow also runs every 15 minutes to detect newly eligible releases and promote releases whose 168-hour deadline has passed; if the release IDs match a healthy active snapshot, it skips package downloads, index generation, signing and publication. The Worker verifies active snapshot eligibility and every stored index object's size, SHA-256 and identity metadata before reporting it as healthy. A manual dispatch may set `force_refresh` to rebuild unchanged metadata, such as when an operator needs to repair a damaged active snapshot. For recovery, dispatch this workflow from `main` with operation `rollback`, choose exactly one channel, and provide its full retained snapshot ID; the protected signing job revalidates the existing manifest, channel eligibility, and every R2 object hash before atomically restoring that channel pointer. No package bytes or GitHub Release assets are rebuilt or replaced.
5. **Prune repository storage** runs weekly at 03:25 UTC Sunday or by manually dispatching operation `prune`, under the protected `aptto-signing` environment and the same workflow concurrency group as publication and rollback. Activation history tracks the six most recently activated snapshots per channel. Each run verifies the active manifest, eligibility and every active R2 object; rollback activation repeats those checks before switching pointers. From history, retention keeps only complete snapshots whose package releases remain eligible and removes older unreferenced objects. It processes at most 50 expired snapshots and 50 expired builds per channel per run, returning pending counts so a backlog can be cleared by later weekly runs or a manual prune. It keeps only the newest registered unsigned build during its first 24 hours, then removes it and older build staging. The release reconciler separately retains package and source R2 staging copies for 30 days after public publication; it deletes those copies only after auditing the immutable GitHub binary and source releases and their asset hashes. If a public audit fails, the R2 recovery copies remain and the reconciler retries later. A manual prune can run snapshot/build cleanup outside the weekly schedule.
6. Confirm the workflow run and Worker responses for both channels. The public index must exclude sponsor-period binaries; the early index and binary downloads must require valid sponsor credentials. Test invalid, expired, and anonymous credentials and verify that no redirect or cache path exposes a gated binary.
7. Install from a fresh focal amd64 client with the published keyring and scoped `Signed-By` configuration. Test anonymous libarchive installation and sponsor-authenticated libxml2 installation, `apt-get source`, package checksums, cross-host redirects, and post-promotion URLs. Record exact client output and workflow IDs.

## Recovery and key custody

- If package verification, private staging, signing, or snapshot activation fails, stop the release path and retain the previous active snapshot. Do not retry by changing bytes under an existing package version or snapshot ID.
- A rollback changes repository metadata only; it does not downgrade packages already installed by clients, and clients may retain signed metadata caches for up to five minutes. After activation, verify the channel's `InRelease` and run `apt-get update` on a clean client. The Worker rejects a snapshot whose releases are no longer eligible or whose stored bytes fail manifest readback. Snapshot/build retention and the 30-day public-release staging interval are implemented in source but remain inactive until the Worker, R2 binding and protected GitHub environments are deployed and verified. Do not claim production cleanup until the protected retention workflow and release reconciler have run successfully against the real bucket.
- Keep the metadata signing key only in the protected `aptto-signing` environment. Record the public key fingerprint and published keyring checksum. For rotation, prepare the replacement key and client trust transition, verify a signed test snapshot, then follow the separately reviewed rotation procedure; no production key or rotation has been configured yet.
- Package release tags are accepted only when GitHub verifies the annotated tag and its tagger resolves to `APTTO_RELEASE_TAG_SIGNER`; GitHub may return no account association for an email, and in that case publication stops. Keep the maintainer's GitHub account limited to the specifically approved release-signing keys and ensure the tagger email is associated with that account. Rotate a package tag key by first registering and testing the replacement key on the approved account; changing the allowed GitHub account requires a separate review and configuration update. The allowlist is account-level, not a pinned GPG fingerprint; no production signer account or tag key is configured yet.
- On suspected key compromise, disable the signing environment and stop snapshot publication. Preserve evidence and the last known-good snapshot; do not publish an unreviewed replacement key or claim old package copies were revoked.
