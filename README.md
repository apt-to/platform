# GetPatched platform

Public source and reproducible packaging, with a signed APT archive for selected maintained packages.

The only configured pilot target is Ubuntu 20.04 (focal), amd64. The package recipe and policy schemas model independent Ubuntu/Debian release and amd64/arm64 targets; each added combination needs its own source pins, clean build, installed regressions, scans, APT client test, and repository Worker/snapshot routing before publication is enabled. The initial candidates are libxml2 (seven-day sponsor-first binaries) and libarchive (public after release checks). All source recipes remain public from the start. Public binaries will be served from GitHub Releases; private staging will use Cloudflare R2.

This is an implementation in progress. No package is claimed fixed or supported until its release evidence is published.

The current verification record and open acceptance gates are indexed in [`EVIDENCE.md`](EVIDENCE.md); see [`STATUS.md`](STATUS.md) for the latest checkpoint.

## Source preflight

`python3 scripts/inspect-ubuntu.py` records the currently published focal source-package metadata from Launchpad, descriptor hashes, and archive checksums/sizes from the source descriptors. It downloads small descriptors, uses no credentials, and does not mutate the archive. Descriptor signatures are not verified by this helper; archive bytes must be verified against the recorded hashes when imported. Its JSON output is suitable for saving as preflight evidence.

## Candidate baseline scans

On a disposable Linux Docker host, run `python3 scripts/run-baseline.py --package libxml2 --output evidence/baseline-libxml2` (or `libarchive`). The helper installs the exact current public candidate, fails if the archive candidate changes, and retains the unfiltered Trivy report, identified packages, database hashes and reusable `scanner-db/` snapshot. It creates and removes its own baseline image and temporary scan directory. Base/scanner images remain available to the disposable runner until that runner is destroyed.

Reuse the snapshot with `--database-snapshot PATH/TO/scanner-db` and a fresh output directory; this disables database updates. Before/after remediation comparisons must use the same snapshot and scanner, and preserve their raw reports. The manual `Candidate baseline scans` workflow stores JSON and database snapshots as separate immutable run artifacts for 30 days; retain the matching snapshot with final release evidence before that expiry. These artifacts contain public baseline reports and public vulnerability databases, never GetPatched binary builds.

The raw baseline scan may not identify the target CVE in Trivy; it still preserves the full vendor report and package inventory. Do not read an empty Trivy target list as evidence of a fix. Trivy's OS-package scanner follows distribution advisory sources and does not provide a custom feed for GetPatched's backported dpkg packages, so the platform also publishes a versioned OSV-format feed at `advisories/getpatched-osv.json` and a public scanner: `python3 scripts/getpatched-scan.py --status-file /var/lib/dpkg/status --release focal --architecture amd64`. It reads installed dpkg records, uses Debian version ordering, reports findings with exit status 1, reports a clean target scan with 0, and rejects malformed or policy-mismatched feeds with 2. Its report includes the feed, package-policy and status-file hashes. The package verification workflow runs this scanner against the actual baseline and patched container status databases, binds reports to the image IDs, requires every target CVE on the baseline and none on the patched package, and retains both scan reports. Raw Trivy JSON remains separately untouched. Ubuntu's OSV assessment is also retained; GetPatched's finding status reflects the exact installed backport and regression evidence, not a change to Canonical's advisory data.

## Development package verification

Clone the public recipe repository `getpatched/packaging-libxml2` or `getpatched/packaging-libarchive` and check out its `getpatched/focal` branch. Schema-version-3 `package-manifest.json` points to one file per target, such as `targets/ubuntu/focal-amd64.json`; `patches/metadata.json` binds each patch to an explicit target and exact source version or Debian-version range, with CVEs only on security patches. The target's supported-source-version allowlist and build evidence remain mandatory even when a patch has a range. The builder downloads the pinned Ubuntu source package, checks each file, extracts it in the pinned focal build container, then applies selected recipe patches while preserving Ubuntu's original Debian packaging. The pre-recipe full-source snapshot remains on each package repository's `legacy` branch. With a clean, committed recipe checkout and a disposable Linux Docker host, run `python3 scripts/build-package.py --source /path/to/packaging-checkout --target ubuntu-focal-amd64 --output build/output`.

The current recipes support one exact Focal source version each. The target file records the base, output version, and release serial; a same-base rebuild advances `+getpatched1` to `+getpatched2`, while every additional distribution source version or architecture needs its own target pin and passing applicability/regression evidence. A version range by itself is never treated as proof that a patch applies.

Every active individual GitHub Sponsors tier qualifies for sponsor-first targets; there is no tier allowlist or minimum amount. Organization sponsorships are not yet supported because the service cannot securely map one to a specific GitHub user; organization membership alone never grants access. A one-time sponsorship qualifies only while GitHub reports it active. Official early binaries may be used privately and commercially, but GetPatched does not permit redistribution of its official early-channel binaries until public promotion; upstream and distribution license rights remain intact. Access ends when GitHub reports the sponsorship inactive; copies already downloaded cannot be recalled. GetPatched-authored code, schemas, recipes, patches, tests, and documentation are MIT-licensed from day one. On public promotion, GetPatched-authored contributions in the official binaries are MIT; upstream and distribution licenses and notices continue to apply. See each package's versioned `LICENSES/GETPATCHED-EARLY-ACCESS-1.2.md`.

The build dependencies come from the official Ubuntu archive snapshot recorded in `packages.json`. The base and trust-bundle images are pinned by digest. The helper records the resulting builder image ID, installed toolchain and Debian `.buildinfo`; native package compilation/testing runs with networking disabled. It requires a reproduced installed-baseline regression before building, then installs its own outputs for patched regressions, consumer checks and Debian version comparisons. It assembles the actual `.deb`, `.dsc` and source tarballs into a temporary focal archive, signs it with the reusable APT metadata signer and an ephemeral test key, then asks a clean pinned focal client to verify `InRelease`/`Release.gpg`, install the exact binary packages, and fetch the source package through `deb-src`. The archive and key are discarded; no test binary is published.

The manual `Package build and installed regressions` workflow performs paired GetPatched, Trivy and Canonical OSV scans plus the signed APT client smoke test. Its JSON artifacts include before/after GetPatched scan reports and their feed/status hashes, both unmodified Trivy reports, exact OSV requests/responses, scan identity/database sidecars, the advisory comparison and temporary signed-repository smoke summary. Candidate binaries stay out of public workflow artifacts. On `main`, a successful manually dispatched verification can trigger `Private binary staging`: the protected workflow rebuilds the exact source commit, compares candidate hashes, then submits the verified binaries and public source to the Worker for private R2 staging. That path is disabled until its repository variable, Worker endpoint/bucket, OIDC trust and protected environment secrets are configured. Development backports are not releases: production signing, storage, access and promotion gates must still pass.

## Public catalogue preview

`site/` contains the public package catalogue UI and its policy-backed data. Preview it locally with `python3 -m http.server 8765 --directory site`, then open `http://127.0.0.1:8765/`. The page reports development checks as passed while keeping release verification and production publication explicitly open; it must not expose install commands or binary links until the signed production repository is available. The `Platform quality` workflow checks that catalogue versions, CVEs, target and access delays stay aligned with `packages.json`.

The public catalogue and source links do not depend on GitHub Sponsors, and the site is now deployed at `https://getpatched.dev`. The Worker and static site deployed from `main` at commit `84970a37c7d43ca49b311f627b51e2b6e803abf1`; the public smoke checks for `/` and `/account` passed. The account page accurately reports that GitHub sign-in is unavailable until OAuth is configured. Repository metadata is not yet published: the public Focal `InRelease` endpoint currently returns HTTP 503 and the unauthenticated early endpoint returns HTTP 401. The production workflow now deploys automatically after verified pushes to `main`; see the operations runbook for its ongoing-token and package-release requirements. Do not repeat the nameserver change, import records from the former `apt.to` domain, or add guessed DNS records.

`scripts/generate-apt-index.py` can sign a freshly generated immutable snapshot when passed an isolated `GNUPGHOME` and its full signing fingerprint. It emits and verifies both `InRelease` and `Release.gpg`, exports the public key beside the repository, and refuses unsafe key fingerprints or missing keys. Keep the long-lived private signing key in the protected `getpatched-signing` environment; never send it through the release Worker or store it in R2. The public key and primary fingerprint are published at [`/keys/getpatched-archive-key.asc`](https://getpatched.dev/keys/getpatched-archive-key.asc) and [`/keys/getpatched-archive-key-fingerprint.txt`](https://getpatched.dev/keys/getpatched-archive-key-fingerprint.txt); verify the fingerprint over an independent channel before trusting it. A protected two-job workflow builds unsigned indexes in a no-key job, then signs and publishes hash-checked metadata in a separate job using the builder's exact snapshot IDs. Wrangler declares custom domains for `getpatched.dev`, `repo.getpatched.dev`, and `early.getpatched.dev`; the Worker and static site are deployed. The live website and account routes passed smoke checks, while the public APT metadata route returned HTTP 503 and the unauthenticated early route returned HTTP 401. Repository installation and sponsor access remain unavailable until signed package metadata and sponsor credentials are configured. No production snapshot has been signed or published. Do not publish package binaries until the release gates in `BUILD_SPEC.md` pass.

## Release state worker (integration in progress)

`worker/` contains the current R2-backed release-state adapter and a 15-minute Cloudflare Cron Trigger. It uses conditional R2 writes for compare-and-swap state updates, checks a successful package-verification Actions run, binds that run to the exact signed tag and source commit on the configured package branch, uploads staged immediate-public assets to draft GitHub Releases, reads them back to check SHA-256, and publishes only when GitHub immutable releases are enabled. The reconciler audits already-published release bytes against the recorded hashes. Configure the private R2 binding and two Cloudflare Worker secrets before enabling package release operations: `GITHUB_ACTIONS_TOKEN` needs Actions read access only on `getpatched/platform`; `GITHUB_RELEASE_TOKEN` needs Contents read/write and Administration read on the packaging repositories (`packaging-libxml2`, `packaging-libarchive`, `packaging-libpng1.6`, `packaging-libgit2`, `packaging-tiff`, and `packaging-poppler`). The Worker accepts tokens directly and does not mint or refresh GitHub App installation tokens. `GITHUB_TOKEN` is a temporary compatibility fallback; remove it after both purpose-specific secrets are configured. Keep optional `RELEASE_ADMIN_TOKEN` unset for routine operations. Do not put token values in this repository or a public workflow log.

The Worker has an authenticated, bounded R2 staging upload endpoint that accepts only manifest-listed assets, derives create-only keys, streams bytes to R2 with SHA-256 validation, and supports integrity-checked retries. It also implements signed sponsorship-cancellation webhook intake, scheduled GitHub Sponsors reconciliation for every active individual sponsor across all tiers (including one-time sponsorships only while GitHub reports them active), GitHub OAuth with state and PKCE, hashed seven-day sessions, revocable per-device APT credentials, sponsor-only asset serving, and an admin-gated transition that starts the exact 168-hour clock after every private asset passes R2 checksum/metadata readback. Organization sponsorships are not yet mapped to a user and therefore do not grant access. The Worker serves the public catalogue and `/account` portal through a static-assets binding. The Worker and site are deployed. The R2 write/read/delete self-test and signing-key verification passed; Focal and Jammy repository routes respond with HTTP 503 while no signed snapshot is published. The repository publication gate remains disabled. Package release token scopes still need to be confirmed; no GitHub App is installed for this organization. No public package metadata or packages have been published, and no live sponsor or seven-day promotion has been tested. Do not treat local unit tests as production release evidence.
