# AptTo

Public source and reproducible packaging, with a signed APT archive for selected maintained packages.

The pilot targets Ubuntu 20.04 (focal), amd64. The initial candidates are libxml2 (seven-day sponsor binary access) and libarchive (immediate public binaries), subject to verified vulnerability and regression preflight. Source remains public from the start. Public binaries will be served from GitHub Releases; private staging will use Cloudflare R2.

This is an implementation in progress. No package is claimed fixed or supported until its release evidence is published.

## Source preflight

`python3 scripts/inspect-ubuntu.py` records the currently published focal source-package metadata from Launchpad, descriptor hashes, and archive checksums/sizes from the source descriptors. It downloads small descriptors, uses no credentials, and does not mutate the archive. Descriptor signatures are not verified by this helper; archive bytes must be verified against the recorded hashes when imported. Its JSON output is suitable for saving as preflight evidence.

## Candidate baseline scans

On a disposable Linux Docker host, run `python3 scripts/run-baseline.py --package libxml2 --output evidence/baseline-libxml2` (or `libarchive`). The helper installs the exact current public candidate, fails if the archive candidate changes, and retains the unfiltered Trivy report, identified packages, database hashes and reusable `scanner-db/` snapshot. It creates and removes its own baseline image and temporary scan directory. Base/scanner images remain available to the disposable runner until that runner is destroyed.

Reuse the snapshot with `--database-snapshot PATH/TO/scanner-db` and a fresh output directory; this disables database updates. Before/after remediation comparisons must use the same snapshot and scanner, and preserve their raw reports. The manual `Candidate baseline scans` workflow stores JSON and database snapshots as separate immutable run artifacts for 30 days; retain the matching snapshot with final release evidence before that expiry. These artifacts contain public baseline reports and public vulnerability databases, never AptTo binary builds.

The raw baseline scan may not identify the target CVE in Trivy; it still preserves the full vendor report and package inventory. Do not read an empty Trivy target list as evidence of a fix. Trivy's OS-package scanner follows distribution advisory sources and does not provide a custom feed for AptTo's backported dpkg packages, so the platform also publishes a versioned OSV-format feed at `advisories/aptto-osv.json` and a public scanner: `python3 scripts/aptto-scan.py --status-file /var/lib/dpkg/status --release focal --architecture amd64`. It reads installed dpkg records, uses Debian version ordering, reports findings with exit status 1, reports a clean target scan with 0, and rejects malformed or policy-mismatched feeds with 2. Its report includes the feed, package-policy and status-file hashes. The package verification workflow runs this scanner against the actual baseline and patched container status databases, binds reports to the image IDs, requires every target CVE on the baseline and none on the patched package, and retains both scan reports. Raw Trivy JSON remains separately untouched. Ubuntu's OSV assessment is also retained; AptTo's finding status reflects the exact installed backport and regression evidence, not a change to Canonical's advisory data.

## Development package verification

Clone the public `apt-to/packaging-libxml2` or `apt-to/packaging-libarchive` repository and check out its `aptto/focal` branch. With a clean, committed checkout and a disposable Linux Docker host, run `python3 scripts/build-package.py --source /path/to/packaging-checkout --output build/output`.

The build dependencies come from the official Ubuntu archive snapshot recorded in `packages.json`. The base and trust-bundle images are pinned by digest. The helper records the resulting builder image ID, installed toolchain and Debian `.buildinfo`; native package compilation/testing runs with networking disabled. It requires a reproduced installed-baseline regression before building, then installs its own outputs for patched regressions, consumer checks and Debian version comparisons. It assembles the actual `.deb`, `.dsc` and source tarballs into a temporary focal archive, signs it with the reusable APT metadata signer and an ephemeral test key, then asks a clean pinned focal client to verify `InRelease`/`Release.gpg`, install the exact binary packages, and fetch the source package through `deb-src`. The archive and key are discarded; no test binary is published.

The manual `Package build and installed regressions` workflow performs paired AptTo, Trivy and Canonical OSV scans plus the signed APT client smoke test. Its JSON artifacts include before/after AptTo scan reports and their feed/status hashes, both unmodified Trivy reports, exact OSV requests/responses, scan identity/database sidecars, the advisory comparison and temporary signed-repository smoke summary. Candidate binaries stay out of public workflow artifacts. On `main`, a successful manually dispatched verification can trigger `Private binary staging`: the protected workflow rebuilds the exact source commit, compares candidate hashes, then submits the verified binaries and public source to the Worker for private R2 staging. That path is disabled until its repository variable, Worker endpoint/bucket, OIDC trust and protected environment secrets are configured. Development backports are not releases: production signing, storage, access and promotion gates must still pass.

## Public catalogue preview

`site/` contains the public package catalogue UI and its policy-backed data. Preview it locally with `python3 -m http.server 8765 --directory site`, then open `http://127.0.0.1:8765/`. The page reports development checks as passed while keeping release verification and production publication explicitly open; it must not expose install commands or binary links until the signed production repository is available. The `Platform quality` workflow checks that catalogue versions, CVEs, target and access delays stay aligned with `packages.json`.

The catalogue source is ready for deployment, but it is not live on `apt.to`. The Cloudflare account and existing zone were verified read-only by ID; the zone is pending and DNS remains delegated to Afternic. Recheck the account inventory and route plan before deployment; no DNS change has been made.

`scripts/generate-apt-index.py` can sign a freshly generated immutable snapshot when passed an isolated `GNUPGHOME` and its full signing fingerprint. It emits and verifies both `InRelease` and `Release.gpg`, exports the public key beside the repository, and refuses unsafe key fingerprints or missing keys. Keep the long-lived private signing key in a protected signing environment; never send it through the release Worker or store it in R2. A protected two-job workflow now builds unsigned indexes in a no-key job, then signs and publishes hash-checked metadata in a separate job using the builder's exact snapshot IDs. Wrangler declares custom domains for `apt.to`, `repo.apt.to`, and `early.apt.to`, preparing the site, sponsor portal, and both archive channels. These local settings and routes have not been deployed or verified against Cloudflare, R2, or a live APT client. The existing Cloudflare zone is pending and public DNS remains delegated to Afternic, so production installation is not available. Do not change nameservers or deploy custom domains until the service inventory and preservation plan are approved.

## Release state worker (integration in progress)

`worker/` contains the current R2-backed release-state adapter and a 15-minute Cloudflare Cron Trigger. It uses conditional R2 writes for compare-and-swap state updates, checks a successful package-verification Actions run, binds that run to the exact signed tag and source commit on `aptto/focal`, uploads staged immediate-public assets to draft GitHub Releases, reads them back to check SHA-256, and publishes only when GitHub immutable releases are enabled. The reconciler audits already-published release bytes against the recorded hashes. Configure the R2 bucket binding and Worker secrets `GITHUB_TOKEN` (GitHub App permissions: Actions read on `apt-to/platform`; Contents read/write and Administration read on the two packaging repositories) and `RELEASE_ADMIN_TOKEN` before deployment. Do not put either value in this repository or a public workflow log.

The Worker has an authenticated, bounded R2 staging upload endpoint that accepts only manifest-listed assets, derives create-only keys, streams bytes to R2 with SHA-256 validation, and supports integrity-checked retries. It also implements signed sponsorship-cancellation webhook intake, scheduled GitHub Sponsors reconciliation against an explicit eligible-tier allowlist, GitHub OAuth with state and PKCE, hashed seven-day sessions, revocable per-device APT credentials, sponsor-only asset serving, and an admin-gated transition that starts the exact 168-hour clock after every private asset passes R2 checksum/metadata readback. The Worker serves the public catalogue and `/account` portal through a static-assets binding. Local tests cover these paths, but no GitHub Sponsors listing or production credentials, R2 bucket, or Worker deployment is configured. Private staging is wired to a protected workflow but disabled until its service inputs are configured. Signed snapshot publication and public/early repository routing are implemented and locally tested; no hosted R2, live sponsor, seven-day promotion, or focal-client acceptance test has run. Do not treat local unit tests as production release evidence.
